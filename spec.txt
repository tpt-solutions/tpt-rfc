# RFC → Rust Crate Coverage Survey

Survey date: 2026-08-13. Bar for "Good": actively maintained (release/commit
within ~18 months), reasonably adopted, licensed to cover **both** the MIT
and Apache-2.0 crowds (dual MIT/Apache-2.0, or MIT-only — but **not**
Apache-2.0-only, since that fails MIT-only consumers), and a spec-complete
implementation (not a partial subset). All license/maintenance claims below
were verified live against crates.io/docs.rs/GitHub during research, not
from memory.

Legend: **Good** = meets the bar. **Partial** = usable but fails one bar
(stale, incomplete, wrong license, or subset-only). **Gap** = nothing
suitable found.

## Deeper nuance on specific areas

- **CBOR licensing/maintenance**: `ciborium` is **single-licensed Apache-2.0**
  — under the MIT-crowd requirement, it doesn't clear the bar at all, not
  just "worth noting." Maintenance is otherwise fine (active GitHub commits
  into mid-2026) but the crates.io-published version has been stale since
  Jan 2024, so anyone relying on the published crate (not a git dependency)
  is trusting an old snapshot regardless of license. `serde_cbor` is the
  correctly dual MIT/Apache alternative but is deprecated/unmaintained
  (>5yr stale). Net result: **no actively-maintained CBOR crate satisfies
  both the MIT bar and the freshness bar at once** — this is a real gap,
  not just a nuance.

- **JWK/JOSE fragmentation**: this is a structural gap, not just a
  maintenance one. The RFCs split cleanly into JWS (7515) / JWE (7516) / JWK
  (7517) / JWA (7518), but no Rust crate mirrors that separation with
  composable primitives (the way RustCrypto separates hash/MAC/cipher
  traits). `josekit` bundles all four monolithically; `biscuit` bundles
  JWS+JWE but admits incomplete algorithm/path coverage; `jsonwebtoken` only
  covers JWS-shaped JWT and ignores JWK/JWE entirely. Picking "verify JWTs"
  vs "full JOSE stack with JWKS-based key rotation" means picking an entirely
  different crate, not adding a feature flag.

- **MIME/email**: well covered — `mail-parser` implements RFC 5322 + MIME
  (2045-2049) together, Apache/MIT, actively maintained, no known parsing
  gaps. Building (not just parsing) MIME messages is handled by `mail-builder`
  in the same Stalwart family — confirm its license/maintenance matches if
  that matters, but this is the strongest, most coherent cluster in the
  whole survey.

- **Strict URI parsing (RFC 3986)**: a gap in adoption, not correctness.
  `iri-string` is the spec-faithful RFC 3986/3987 parser (MIT/Apache) but has
  a fraction of `url`'s adoption (198M vs 794M downloads) because `url`
  implements the WHATWG URL Standard, not strict 3986, and deviates from it
  in edge cases. Anyone needing actual RFC 3986 semantics (vs browser-URL
  semantics) should reach for `iri-string`, against the ecosystem default.

- **Unified base encoding (RFC 4648)**: popularity and completeness point
  to different crates. `data-encoding` is the actual "unified" crate
  (base16/32/32hex/64/64url/hex all in one, MIT) but is 4x less downloaded
  than `base64`, which only covers base64 variants. If full RFC 4648
  grammar coverage in one dependency matters, `data-encoding` is correct;
  if you just need base64, the popular default is fine.

- **OAuth2/OIDC modularity**: `openidconnect` is a genuine dependency-based
  layer on `oauth2` (same author, shared `SyncHttpClient`/`AsyncHttpClient`
  trait abstraction, re-exported token types) rather than a parallel
  reimplementation — the cleanest core/layer composability example found in
  this whole survey. A codebase already on `oauth2` for pure OAuth2 flows can
  adopt `openidconnect` incrementally. The competing `openid` (kilork) crate
  is well-maintained with a faster release cadence but owns its own OAuth2
  core instead of composing with `oauth2` — better if you want more
  built-ins (TLS backends, Microsoft-specific quirks) in one crate, worse if
  ecosystem-wide reuse is the priority. Note the underlying `oauth2` crate's
  ~19-month release staleness propagates to `openidconnect` since it depends
  directly on it.

- **SSH (RFC 4251-4254) under the MIT-crowd rule**: `russh` is the only
  pure-Rust implementation with both client+server and an
  embeddable/extensible protocol layer, but it's **Apache-2.0 only**, so it
  fails outright for MIT-only consumers. `ssh2` (MIT OR Apache-2.0) is the
  sole dual-licensed option, but it's a client-only FFI wrapper around C
  libssh2 — no server mode, no protocol-layer extensibility, and its C
  dependency isn't covered by Rust security tooling. There is currently no
  crate that is simultaneously dual-licensed, pure Rust, and offers a server.

## Gaps worth building a crate for

Ranked by how concrete the demand signal is:

1. **RFC 8949 CBOR under a proper MIT/Apache dual license** — `ciborium`
   is Apache-2.0 only and thus fails the MIT-crowd bar outright, despite
   being the best-maintained CBOR implementation. `serde_cbor` is correctly
   dual-licensed but dead. A maintained, dual MIT/Apache CBOR crate (or
   ciborium re-licensing, if upstream would consider it) is a concrete gap
   for anyone who can't accept Apache-2.0-only dependencies.

2. **RFC 4251-4254 SSH, dual-licensed, with server support** — `russh`
   (the only full-featured pure-Rust option) is Apache-2.0 only; the one
   dual-licensed crate (`ssh2`) is a client-only C binding. A dual
   MIT/Apache pure-Rust SSH server (or a relicense negotiation with russh's
   maintainers) would close a real gap — SSH servers are common
   infrastructure and there's currently no MIT-compatible pure-Rust path.

3. **RFC 4226 HOTP** — TOTP is well covered (totp-rs) but there's no
   mature, well-adopted, actively-maintained, clean-MIT/Apache HOTP
   implementation. Existing candidates (rust-otp, otp-rs) are low-download
   or stale. A small, focused `hotp` crate with a clean API (mirroring
   totp-rs's ergonomics) would fill a real gap — HOTP is still used for
   hardware tokens (e.g. YubiKey) and this is a well-specified, low-surface
   RFC to implement correctly.

4. **RFC 5280 X.509 full chain/path validation under MIT/Apache** —
   the only crate that does full validation (rustls-webpki) is ISC-only;
   the MIT/Apache parsers (x509-parser, x509-cert) stop at decoding. Anyone
   needing strict dual-permissive licensing for validation currently has
   no option. This is a bigger lift (path building, trust anchors,
   revocation/CRL/OCSP) but high-value given how foundational X.509 is.

5. **RFC 8032 Ed25519 without relying on BSD-3-Clause dalek** —
   ed25519-compact already exists and is a good MIT-licensed option, so
   this is a *lower priority* gap (mostly closed), but it's much less
   battle-tested/adopted than dalek. Worth noting rather than building —
   contributing audits/adoption to ed25519-compact may be more valuable
   than a new crate.

6. **RFC 3501 IMAP4 server** — no maintained server-side IMAP
   implementation exists in the Rust ecosystem at all (only client crates).
   This is a large surface (full IMAP command set, mailbox storage
   semantics) but a genuine, complete gap — anyone building a Rust mail
   server today has to drop to C libraries or roll their own.

7. **RFC 8484 DNS-over-HTTPS as a dedicated crate** — currently only
   available bundled as a hickory-resolver feature; standalone attempts
   are stale or wrongly licensed. A thin, focused, MIT/Apache DoH client
   crate (could even wrap hickory + reqwest/hyper) would be a
   comparatively small, high-clarity project.

8. **RFC 9111 HTTP caching semantics under MIT/Apache** — the correct
   logic exists (http-cache-semantics) but is BSD-2-Clause. A clean-room
   MIT/Apache reimplementation of RFC 9111 freshness/validation rules
   would unblock strict-license consumers; moderate spec complexity
   (freshness lifetime calc, validators, vary handling, request
   directives).

9. **RFC 2131 DHCP client/server (not just wire codec)** — dhcproto
   covers packet encode/decode well but there's no full client or server
   built on it in the mainstream ecosystem (only a separate WIP "dora"
   project). Lower priority unless you specifically need DHCP tooling.

## Notable license traps found during this survey

These are worth flagging since they're commonly (and incorrectly) assumed
to be MIT/Apache-2.0 by people skimming the ecosystem:

- **ed25519-dalek** — BSD-3-Clause, not MIT/Apache.
- **ring** — "Apache-2.0 AND ISC" mixed, not clean MIT/Apache.
- **rustls-webpki** — ISC only.
- **http-cache-semantics** — BSD-2-Clause.
- **doh-client** — BSD-3-Clause.
- **ciborium** — Apache-2.0 only, no MIT option (fails MIT-only consumers).
- **russh** — Apache-2.0 only, no MIT option.
- **openssl (rust-openssl)** — Apache-2.0 only, no MIT option (moot here since rustls covers TLS with a proper dual license).

## Other flags

- **rsa (RFC 8017)** has an open, unpatched timing side-channel advisory
  (RUSTSEC-2023-0071, "Marvin Attack") as of this survey — usable but not
  safe against network-observable timing attackers.
- **oauth2 (ramosbugs)** is feature-complete but hasn't cut a release in
  ~19 months (repo still has commits, so not abandoned — just release-stale).
- Stalwart Labs' mail-parser / mail-send / mail-auth form the strongest,
  most coherent, actively-maintained dual-licensed cluster found in this
  entire survey.
